# app 财报提示 — 设计

日期：2026-10-11 · 状态：待用户审阅

## 目标

在手机 app 里提醒「框架池里哪些票刚出财报 / 快出财报」，并一键开调研对话。
财报提醒从此只在 app 里出现：飞书财报提醒整套下线。异动提示另议，本次不做。

成功标准：

- 发布当天按发布时段和时钟判定「已出」，不等 longbridge 财务数据入库。
- 有「待看」财报时，首页 ⋯ 按钮出现「!」；菜单有「财报 · N 待看」；财报页分「已出 / 即将发布」两组，每行可一键开调研对话，内置提示词预填进输入框。
- 看页面不调 longbridge；财报日历每天（北京时间）最多全量查一次，约 10 次调用。
- 飞书财报提醒的脚本、判定库、测试和两条 crontab 移除；日报及其飞书推送不受影响。

## 数据源与调用策略

只用 `longbridge finance-calendar report`（每次最多 10 个 `--symbol`）。

- 一次查询返回 `--start` 之后该票全部已知事件（`--end` 实测被忽略），每条带当地日期 `ext.local_date`、发布时段 `ext.financial_report.market_time`（`before` / `during` / `after` / `U`）和期别文案 `content`（如「2026 财年第 3 季度业绩披露」）。
- `--start` 取北京时间今天 − 7 天，覆盖「已出」窗口。
- **刷新时机**：请求到来时，若缓存的查询日期（北京时间）不是今天，就按当前框架池全量查一次；否则零调用。不开后台轮询：不打开 app 就不调。
- 框架池变化不触发查询：新加的框架次日刷新后才出现；删除或改名的票在请求时按当前框架池过滤掉。
- 不做按距离分级的刷新：全量一次约 10 次调用，分级每天最多省几次，不值得为此加逻辑；每天全量也让改期最多晚一天发现。
- 缓存落盘 `output/earnings/calendar.json`（查询时间、每票事件列表），服务端重启不重查。并发请求由锁合并成一次查询（同 `QuoteCache` 做法）。
- 港股代码按日历的写法去掉前导零（`0700.HK` → `700.HK`）再匹配，沿用现有 `normalize_symbol`。
- 不再查 `financial-report --latest`：它的报告期编号与日历期别对不上（台积电日历「第 2 季度」对应 `2026.H1`，AEHR「2026 财年第 4 季度」对应 `2026`），且需逐票调用。

## 「已出 / 即将发布」判定

纯函数，输入缓存事件 + 当前时间，输出每票至多一行。

发布时刻（该市场当地时区，复用 `market_hours.MARKET_TZ`）：

| 时段 | 发布时刻 |
|------|----------|
| `before`（盘前） | 当天开盘：A / HK / US 均为当地 09:30 |
| `during` / `after` / `U` | 当天收盘：A 15:00，HK 16:00，US 16:00（美东） |

- **已出**：发布时刻 ≤ 现在，且当地今天 − 发布日 ≤ 7 天。
- **即将发布**：发布时刻 > 现在，且发布日 − 当地今天 ≤ 3 天（含今天，显示「今天盘后」等）。
- 每票一行：窗口内有已出事件就显示最近一次已出；否则显示最近一次即将发布。同一份财报日历里常有相隔一天的两条（如「第 2 季度」和「半年报」），按此规则只出一行。
- A 股晚间发布的财报按 15:00 判为已出，可能早几个小时；对提醒可接受，调研时 Claude 会发现尚未发布。
- 节假日不建模（同 `market_hours`）。
- app 里已归档的框架不进财报列表。

## 已调研 / 已忽略 / 待看

- **已调研**：对话列表里存在 `kind == "ticker"`、`ticker` 为该票、`created_at` ≥ 该次发布时刻的对话（含已归档对话；从文档页开的也算）。不另存标记。
- **已忽略**：用户在财报页点 ×。存 `output/earnings/ignored.json`，键为（票，发布日），只作用于这一次财报；超出已出窗口的键在下次写入时清掉。可「恢复」。服务端是唯一写者，原子写（同 `FrameworkArchive`）。
- **待看**：已出 且 未调研 且 未忽略。⋯ 的「!」和菜单数字只数待看；即将发布不触发。

## 服务端

新模块 `app/server/lynch_reader/earnings.py`：日历缓存、判定、忽略存储。

- `GET /api/earnings` →
  ```json
  {
    "fetched_at": "2026-10-11T09:02:11+08:00",
    "error": null,
    "items": [{
      "ticker": "TSM.US", "name": "台积电",
      "status": "released",
      "date": "2026-10-14", "slot": "after", "release_at": "2026-10-14T16:00:00-04:00",
      "period": "2026 财年第 3 季度",
      "researched": false, "ignored": false
    }]
  }
  ```
  `status`：`released` | `upcoming`；`slot`：`before` | `during` | `after` | `unknown`；`period` 为 `content` 去掉「业绩披露」。排序：已出按发布时刻倒序，即将发布按发布时刻正序。
- `POST /api/earnings/ignore`、`POST /api/earnings/unignore`，body `{ticker, date}`，走现有 `_guarded`（CSRF）；票须在框架池里。
- 日历拉取放 `eval/lib/earnings_lb.py`：改为返回每票事件列表（日期、时段、期别）；删掉 `fetch_latest_period(s)` 和按窗口挑日期的逻辑；`normalize_symbol` 从将删除的 `earnings_available.py` 移入。

## 前端

- **⋯ 按钮**：运行中对话数字角标留右上；有待看财报时左上另加红色「!」，可并存。
- **菜单**：最上加一行，有待看为「财报 · N 待看」，否则「财报」，进财报页（新路由 `#/earnings`）。
- **取数**：首页挂载时取一次，之后每 5 分钟取一次（判定随时钟变化，服务端零调用）。
- **财报页**：顶栏返回 + 标题「财报」；有 `error` 时顶部提示「财报日历刷新失败：…（显示的是 X 的数据）」。两组：
  - 已出：代码 + 名字；第二行「期别 · 日期 时段」。右侧「调研」；待看行另有 ×（忽略）。已调研 / 已忽略的行变灰并标注，已忽略行的 × 换成「恢复」。
  - 即将发布：同样两行，第二行如「2026 财年第 3 季度 · 今天盘后」；只有「调研」。
  - 点行打开该票框架文档。
- **调研按钮**：把内置提示词写入该票新对话的草稿（复用 `drafts.ts`，键 `new/<TICKER>`）后跳到 `#/chat/new/<TICKER>`；已有未发送草稿时保留原文，提示词接在其后（空一行）。用户可改后发送。

## 内置提示词

放 `app/web/src/earnings/prompts.ts`，一处维护；作为第一条消息出现在对话里。两段模板，填入票、期别、日期时段：

**财报后（已出）**

> {TICKER} 的 {期别} 财报已于 {日期 时段} 发布。请做财报后核对：
> 1. 读 frameworks/{TICKER}.md 的现行结论和 Assumptions。
> 2. 拉本期财报、管理层指引和电话会要点（注明来源）。
> 3. 逐条对照仍为 active 的假设：确认 / 削弱 / 证伪，给出数字证据和来源。
> 4. 指出 §3 可演算块里哪些输入需要改，估计 L/M/H 大致往哪边移、为什么。
> 5. 给结论：框架是否需要修订、改哪几处。
>
> 只在对话里讨论，不写文件；落盘等我说「可以落盘」，再走 sediment-framework。

**财报前（即将发布）**

> {TICKER} 将于 {日期 时段} 发布 {期别} 财报。请做财报前准备：
> 1. 读 frameworks/{TICKER}.md 的现行结论和 Assumptions。
> 2. 列出这次财报会检验的假设；每条写清看哪个数字、到什么程度算确认、到什么程度算削弱。
> 3. 对照市场一致预期和框架的中性情景（M），指出分歧最大的地方。
> 4. 留一份财报出来后回来核对的清单。
>
> 只在对话里讨论，不写文件。

## 错误处理

- 日历整体查询失败：沿用旧缓存，`error` 写明原因和缓存日期；没有任何缓存时 `items` 为空、`error` 非空，菜单只显示「财报」。
- 单批失败：该批的票沿用旧缓存里的事件，其余照常更新，`error` 列出失败的票。
- 只要有失败（整体或单批），查询日期就不推进到今天，下次请求再全量查；但距上次尝试不足 30 分钟不重试，免得首页每 5 分钟的取数反复打 longbridge。
- longbridge 未登录 / 不在 PATH：同整体失败，提示在终端 `longbridge auth login`。
- 日历里缺日期或日期非 ISO 的事件丢弃；未知 `market_time` 按 `unknown` 处理。

## 测试

- `eval/lib`：日历 JSON 解析（时段、期别、港股代码归一、非 ISO 日期丢弃），用录制的样例 payload。
- 服务端（pytest）：
  - 判定：盘前 / 盘后 / 盘中 / 未知各在发布时刻前后翻转；A / HK / US 时区；已出 7 天、即将 3 天边界；同票两条事件只出一行。
  - 缓存：同一天第二次请求不调用拉取函数（框架池变了也不调）；跨北京时间零点会重查；不在当前框架池的票被过滤；单批失败沿用旧数据；有失败时 30 分钟内不重试、之后重试。
  - 已调研 / 已忽略 / 待看：发布前开的对话不算已调研；忽略只作用于该次发布；恢复。
  - 路由：`GET /api/earnings` 形状；ignore / unignore 的 CSRF 与未知票报错。
- 前端（vitest）：提示词模板填充；草稿已有内容时追加；待看计数与菜单文案；路由 `#/earnings` 解析。
- 手动：真机打开 app，确认「!」、菜单、财报页、调研预填；`crontab -l | grep lynch-` 只剩日报两行。
